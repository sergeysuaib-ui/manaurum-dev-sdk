## 1. Итог

1. **Состояние.** SDK хорошо устроен как процесс (CI, мутации, open-claims), но содержание отстаёт от платформы примерно на 4–8 недель. Особенно это касается деплоя, токенов и capabilities. Паттерн MAN-1899 системный, а не разовый. Минимум **восемь фактов** сказаны в 3–12 местах, были верны когда-то и неверны сейчас, причём в другом файле SDK часто уже стоит правда. Это:
   - «нет readiness-пробы»;
   - «неверный порт — зелёный деплой и 502»;
   - «`/agent/*` доступен из интернета»;
   - «упавшая миграция всё равно активирует версию»;
   - «манифест проверяется только в задаче»;
   - wildcard `*` в токенах;
   - `["microphone"]`;
   - «runtime не строгий» (шестая копия, которую 3.1.0 пропустил).
2. **Проблема №1: безопасность, SDK и платформа вместе.**
   - Стартер принимает `user_context`, выпущенный для любого приложения и тенанта: `app_id` и `tenant_id` не сверяются.
   - Шлюз пропускает клиентский заголовок `X-Manaurum-User-Context` в контейнер, и контейнер видит клиентскую копию первой.
   - MAN-1307 (SEC-LOW) покрывает только привязку; проброс заголовка — новое.
3. **Проблема №2: справочник capabilities.**
   - По описанию SDK `os.files.upload`, `os.ocr.extract` и `os.apps.call` всегда получают 422.
   - Код, читающий `usage` из `os.ai.complete`/`os.ai.embed`, падает на успешном ответе.
   - 6 из 32 зарегистрированных capabilities не описаны.
   - SDK учит подписываться на события, хотя приложение не может их получать (В28).
4. **Проблема №3: деплой, токены и откат описаны по состоянию до сентября.**
   - Рецепт выпуска `mna_*` из SDK не выпускает ничего: wildcard запрещён, для первого деплоя нужен `scope_kind:"owner"`.
   - Синхронные отказы деплоя (422/409/413) не перечислены.
   - Повторный деплой той же версии — 409.
   - У отката описан неверный контракт.
5. **Линтеры дают ложную уверенность.**
   - Правило против вшитого `mna_*` не матчит ни одного настоящего токена.
   - Маршруты с `{param}` проходят линтер, а на шлюзе дают 404.
   - Без CLI проверка миграций ловит почти ничего.
6. **На этой машине установлен плагин 2.7.2.** Он учит удалённый v1-путь и «нестрогий runtime». Сигнализатор версии этого не видит.
7. **Процесс.** Исправления части находок уже месяц лежат в открытых PR SDK (#16, #17, #20; MAN-1452, MAN-1923, MAN-2144, MAN-1958/1959). Тем временем main выпустил 2.8–3.1 мимо них.

## 3. Системные рекомендации: как не допускать дрейфа

**Что CI может сверять автоматически.** Нужен снапшот контракта: MAN-2534 и MAN-2857 про это. Монорепа публикует `contract.json` (артефакт релиза или файл в `frontend/public/sdk/`), SDK вендорит его в `contract/` с SHA источника. В нём:
1. `manifest_v2.schema.json`. Тесты:
   - `RUNTIME_KEYS` и корневые ключи в `check_app` равны схеме;
   - каждое поле схемы упомянуто в `V2P`;
   - enum `permissions`, `data.*`, `runtime.mode` в тексте равны схеме (ловит В10, В11, В23, С14).
2. **Реестр capabilities**: имена и JSON-схемы входа из `registration.py`. Тесты:
   - каждое имя имеет раздел в `CR`;
   - пример входа в `CR` валиден по схеме — для этого примеры надо сделать машиночитаемыми, fenced `json` с меткой (ловит К2, К3, К4, К5, С1);
   - `check_app` проверяет имена по реестру (С4).
3. **Коды ошибок** шлюза, capability-шлюза и деплоя: отпечаток литералов `detail` и `error` из `v2_app_gateway.py`, `capability_gateway.py`, `dev_v2_deploy.py`, `owner_deploy.py`, `v2_credentials.py`. Тест: каждый код в таблицах SDK существует, каждый код из отпечатка где-то описан (В7, В24, С8).
4. **Типы postMessage** из `iframeHostPolicy.ts`/`IframeAppHost.tsx`: каждый описан в `sdk-api.md`, и `preview.py` их шлёт (С12).
5. **Формат токенов** (`mna_<12hex>_…`). Мутация строится из него (В2).
6. **`api_route_matcher` и `migration_validator`**: использовать сами функции платформы (вендорить), а не регэкспы (В19, С17).

**Бан-лист фраз в `check_repo.py`**: утверждения, которые уже раз оказались ложными, с каноническим местом правды:
- «no readiness probe»
- «green deploy … 502»
- «not strict»
- «public internet» / «Traefik straight to»
- «still activates»
- `"apps":["*"]`
- `["microphone"]`
- «gateway rejects … user_context»
- «no workspace_id»
- «DROP everything else»

Расширить скан на `templates/**` (README, BRIEF, docstrings стартера и `check_app`): сейчас там живёт треть дублей (Н4).

**Свести дубли к одному источнику.**

| Факт | Единственный источник | Остальные места |
|---|---|---|
| Правила `user_context` и привязка app/tenant | `ST/src/auth.py` + `V2P §auth` | ссылка |
| Пробы, гейт миграций, синхронные и асинхронные отказы, откат | `DEP` (жизненный цикл деплоя) | `SKILL`, `publishing.md`, `README` — одна строка со ссылкой |
| Манифест (ключи, enum, строгость) | `V2P §1-2`, генерируется из схемы | — |
| Миграции | `V2P §7` | — |
| Коды ошибок capabilities и пересылка `user_context` | `CR` | — |
| Токены `mna_*` (scope, owner, лимиты) | `DEP §token` | — |
| `/agent/*`: почему проверять JWT | `V2P` (одна фраза) | — |
| Блок `deploy.sh` (tar/base64/curl) | `DEP` | сейчас три копии |
| Список исключений упаковщика | один | сейчас три |
| Расположение `.env.manaurum` | один | — |

**open-claims.** Хранить не только тикет, но и проверяемый факт («`cli-v0.3.0` — последний релиз», «enum = microphone»), чтобы строка падала, когда факт меняется (В21).

**Процесс.**
- PR #16, #17, #20 висят с августа, а релизы 2.8–3.1 шли мимо них. Нужно правило: перед релизом разобрать открытые doc-PR (влить, перенести или закрыть). Сейчас SDK-тикеты в Linear (MAN-1452, MAN-1923, MAN-2144, MAN-2995, MAN-2600, MAN-2198, MAN-1328, MAN-3203) никто не сводит с релизами.
- Платформенный PR, меняющий видимое разработчику поведение, должен ставить метку «sdk-impact» и заводить SDK-тикет. Тогда MAN-1369, MAN-1432, MAN-2510, MAN-2597 и MAN-2412 не потерялись бы.
- Обновление плагина на машинах команды: `autoUpdate` для маркетплейса и `version_check` против клона маркетплейса (В22). MAN-3187 (анонс релизов) помогает только людям, но не агентам.
